## 1. Цель работы

Связать браузерный интерфейс с HTTP API: расширить клиент ПР5 операциями изменения (POST/PATCH/DELETE), организовать состояния интерфейса во время асинхронных операций (loading/ready/empty/error), защититься от устаревших ответов и научиться проверять поведение модульно, интеграционно и в браузере. Результат: приложение «Задачи из учебного API», в котором создание, редактирование, смена статуса и удаление выполняются только через сервер.

## 3. Реализация

### 3.1. HTTP-клиент

`src/api-client.js` — перенос решения ПР5 с расширениями: метод нормализуется в верхний регистр и ограничен набором GET, POST, PATCH, DELETE (иначе TypeError до сети); GET с телом запрещён; при наличии `body` выполняется `JSON.stringify` и добавляется `Content-Type: application/json`, без тела заголовок не ставится (лишний Content-Type вызывал бы лишний CORS preflight); сохранены `Accept`, тайм-аут (`AbortSignal.timeout`, объединение с внешним сигналом через `AbortSignal.any`) и виды ошибок. Порядок обработки ответа: `!response.ok` → HTTP-ошибка с полями контракта; `204` → `null` без попытки чтения JSON; затем `Content-Type`, затем разбор JSON с сохранением `SyntaxError` в `cause`.

### 3.2. Доменный API

`src/task-api.js` — чтение из ПР5 плюс операции: `createTask` (POST /tasks, тело без `id` и `completed` — их назначает сервер), `updateTask` (PATCH /tasks/:id с изменяемыми полями), `setTaskCompleted` (PATCH с `{ completed }`), `deleteTask` (DELETE, ожидается строго `null` от 204 — любое тело считается `invalid-response`), `resetDemoData` (POST /debug/reset с проверкой подтверждения), `getTaskById`. У каждого метода последний аргумент `{ signal }`. Любая полученная задача/категория проверяется по схеме (id, title 1–100 после trim, completed, приоритет, categoryId; уникальность id; `meta.total`), нарушение — `ApiError` вида `invalid-response`.

### 3.3. Состояния интерфейса

Контроллер показывает `loading` (панель списка получает `aria-busy="true"`, список скрыт), затем `ready` (карточки и счётчик), `empty` (успешный запрос без результатов — явное сообщение, старые карточки убраны) или `error` (понятное сообщение из `messageForError` и кнопка «Повторить загрузку»). `empty` — не ошибка, а нормальный результат фильтра. Повторная загрузка всегда начинается с `loading`, поэтому старое состояние не остаётся на экране. Ошибка отменённого запроса пользователю не показывается.

### 3.4. Изменение данных

Общая схема мутаций (одна внутренняя функция `runMutation`): блокировка кнопок (`setMutationPending(true)`) → запрос изменения через предметный API → при успехе сообщение «Операция выполнена.» и повторный GET с текущими фильтрами → разблокировка в `finally`. Сервер — единственный источник данных: локальный массив только перезаписывается ответом GET, после перезагрузки страницы изменения на месте (пока работает API). Форма очищается и возвращается в режим создания только после успешного создания/сохранения; невалидная форма запроса не отправляет вовсе.

### 3.5. Защита от устаревшего ответа

Два механизма вместе: перед каждой загрузкой предыдущий `AbortController` отменяется, а каждая загрузка получает последовательный номер; результат применяется только если номер совпал с последним запущенным запросом. Проверка номера нужна даже при отмене: источник данных может не отреагировать на сигнал мгновенно (проверка 27 модульного набора именно это моделирует). Отмена при смене фильтра — управление потоком, а не пользовательская ошибка.

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при ответе 404?**&#8203; Ответ 404 — это успешный HTTP-обмен: сервер доступен и вернул ответ. Promise отклоняется только при сетевом отказе или отмене. Поэтому статус проверяется явно через `response.ok` до чтения тела.
2. **Почему ответ 204 нельзя разбирать `response.json()`?**&#8203; У 204 нет тела; `json()` попытается разобрать пустую строку и упадёт с ошибкой синтаксиса. Клиент возвращает `null` до проверки Content-Type.
3. **Чем `empty` отличается от `error`?**&#8203; `empty` — успешный ответ без результатов (нормальная работа фильтра), данные корректны, их просто ноль. `error` — запрос не выполнен (сеть, тайм-аут, HTTP-код, неверный формат), данных нет, нужна кнопка повтора.
4. **Зачем отменять предыдущий запрос при смене фильтров?**&#8203; Чтобы медленный старый ответ не перезаписал результат нового фильтра (гонка запросов). Отмена через `AbortController` плюс проверка порядкового номера загрузки.
5. **Почему после мутации список повторно запрашивается?**&#8203; Сервер — источник истины: он мог изменить данные иначе, чем ожидает клиент (например, другие параллельные клиенты). Повторный GET с текущими фильтрами показывает только подтверждённое сервером состояние.

## 7. Вывод

Браузерный интерфейс, клиентский модуль и контракт API связаны так: view не знает про сеть, контроллер не трогает DOM, все запросы идут через `createApiClient`, а предметные операции сосредоточены в `task-api.js`. Автоматические проверки: 70 в Node и 14 в браузере — зелёные. Найденные и исправленные ошибки: (1) в выданном `checks/browser.checks.js` функция `waitFor` падала на первом синхронном опросе, когда ожидаемый элемент ещё не мог существовать (создание задачи асинхронно) — исправлена на толерантное ожидание без ослабления утверждений; без исправления набор стабильно давал 12/14 из-за каскада: незавершённый запрос создания попадал в reset следующей проверки; (2) промежуточные прогоны показывали ожидаемые падения нереализованных модулей (13/20 → 21/12 → 23/10 → 33/0) — использованы как ориентир порядка реализации. Осознанные ограничения работы: сервер хранит данные в памяти, после каждой мутации запрашивается весь отфильтрованный список, интерфейс без фреймворка — это границы ПР6, а не ошибки.
