## Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Фактический результат | A, B, C, D, E, F | A, B, C — синхронный код; `demonstrateAwait()` вызывается до `log("C", …)`, поэтому B раньше C, на `await null` функция приостанавливается. Затем микрозадачи: D из `then()`, потом продолжение E после `await`. Таймер F с задержкой 0 — следующая задача цикла событий, а не немедленный вызов, поэтому после всех микрозадач. |

После добавления собственной микрозадачи `G` (строка после вызова `demonstrateAwait()`):
порядок A, B, C, D, E, G, F — `G` встала в очередь микрозадач позже D и E, но раньше задачи таймера.

Отдельно:

- Синхронный код: сообщения A, B, C.
- Микрозадачи: D (обработчик `Promise.resolve().then`), E (продолжение после `await`), G (собственный обработчик).
- Таймер с задержкой 0 не выполняется немедленно: нулевая задержка означает минимальное время постановки задачи, задача выполняется после опустошения стека и всех микрозадач.
- Если удалить один из обработчиков Promise, оставшиеся сообщения сохранят взаимный порядок, но удалённое сообщение исчезнет из вывода; следующая микрозадача поднимется на его место.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | готовый учебный HTTP API: маршруты, фильтры, статусы, ошибки, CORS, отладочные маршруты |
| `src/api-client.js` | транспорт: `ApiError`, `buildUrl`, `createApiClient`/`requestJson` — статусы, Content-Type, JSON, тайм-аут, отмена |
| `src/task-api.js` | предметный слой: маршруты задач и категорий, нормализация фильтров, проверка схемы, параллельная загрузка |
| `src/variant.js` | только данные варианта: номер 8 и фильтры |
| `src/main.js` | контрольный консольный сценарий: загрузка, таблица, контрольная ошибка 404 |

`fetchFn` передаётся в `createApiClient` аргументом, чтобы модульные проверки подменяли сеть подготовленными ответами без реального HTTP. HTTP-ошибки проверяются отдельно от сетевых, потому что отказ `fetch` и ответ с кодом 4xx/5xx — разные события: первый перехватывается в собственном `try` вокруг вызова, вторая обрабатывается после получения `Response`. Разобранный JSON всё равно проверяется по контракту (`isTask`/`isCategory`, уникальность id, `meta.total`), потому что синтаксически корректный JSON может не соответствовать форме данных предметной области.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | валидация через `new URL`, только http/https, без query и hash, лишний завершающий `/` срезается | проверки 04, конфигурация |
| Кодирование query-параметров | `URLSearchParams` внутри `URL`; пропускаются только `undefined`, `null`, `""`; `false` и `0` сохраняются | проверки 02, 03 |
| Заголовок `Accept` | `Accept: application/json` на каждый запрос | проверка 05 |
| Проверка `response.ok` | статус вне 2xx → `ApiError` вида `http` с `status`, `code`, `details`, `url` | проверки 08, 09 |
| Проверка `Content-Type` | успешный ответ без `application/json` → `invalid-response` | проверка 10 |
| Разбор JSON | `response.json()` в `try`; `SyntaxError` сохраняется как `cause` | проверка 11 |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)` объединяется с внешним сигналом через `AbortSignal.any` | проверки 14, интеграция 12 |
| Внешняя отмена | `signal` опций; отмена и тайм-аут различаются по тому, какой сигнал сработал | проверка 15, интеграция 13 |

Проверки схемы: задача — положительный целый `id`, непустой `title` 1–100 после `trim`, булево `completed`, приоритет из `low|medium|high`, положительный целый `categoryId`; категория — `id` и `name` 1–100; коллекция — без повторяющихся `id`, `meta.total` равен длине `data`. Нарушение любой формы → `ApiError` вида `invalid-response`.

## Отладка

Точки останова: до `fetchFn(...)` (проверить собранный `url`), после получения `Response` (проверить `status`, `ok`, `content-type`), перед `response.json()`, в обработчике `catch` (проверить `kind`). Успешный запрос: url `…/tasks?…`, status 200, ok true, JSON разобран. Ошибочный (`/api/tasks/999`): status 404, ok false, payload.error с кодом `TASK_NOT_FOUND`, итоговый `ApiError` с `kind: "http"` и `details: {id: 999}`.

## Вывод

Реализован переиспользуемый HTTP-клиент (`buildUrl`, `requestJson`) и предметный API задач с проверкой схемы; все три автоматических набора зелёные (18 + 26 + 13). Из ошибок исправлены: промежуточный прогон показал 16/10 — падения относились к ещё не реализованному `task-api.js`; в нормализации фильтров `null` сначала ошибочно принимался как пустой набор фильтров, исправлено на `TypeError`. Различия видов ошибок: ожидание Promise — ещё не значение, а будущий результат; HTTP-ошибка — сервер ответил кодом вне 2xx (есть `status`/`code`); сетевая — ответа нет вообще; `invalid-response` — ответ получен, но не JSON или не соответствует схеме; `timeout` — истекло заданное время; `aborted` — отмена внешним сигналом.
